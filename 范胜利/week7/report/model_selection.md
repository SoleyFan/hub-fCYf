# 模型 × 场景选型指南（week7 事件抽取）

> 结论先行：**没有“最好的模型”，只有在“标注量 / 算力 / 延迟 / schema 稳定性 / 输出合法性”
> 这五个约束下的最优解。** 下面每个推荐都对应本仓库实测数字（全量 dev 930 句），
> 不是拍脑袋的经验判断。

---

## 1. 一张表：什么场景用什么模型

| 业务场景 | 首选 | 次选 | 不建议 | 关键依据（实测） |
|---|---|---|---|---|
| **零标注冷启动**，schema 已定，允许调用 API | **API zero-shot**（论元 F1 0.522，3.62 s/句） | API few-shot（0.540，但 token 1.6 倍） | 本地 0.6B zero-shot（0.044~0.117） | 本地小模型中文指令遵循弱；few-shot 只多 1.6pp，token 却从 191.6k 涨到 311k |
| **有 3,000~3,500 条标注、单卡 8 GB**，要最高精度 | **LoRA SFT**（触发 0.900 / 论元 0.697 / 事件 0.185） | BERT+CRF+硬约束（0.657） | 两段式（0.369） | 3,499 条 / 1 epoch / 9 MB adapter，论元超过 5,747 条训练的 BERT 11.7pp |
| **只有 200~500 条标注**，还没到微调规模 | **API few-shot**（0.540） | API zero-shot（0.522） | 从零训 BERT/BiLSTM | 数据量不足以训 149 标签序列标注；提示式模型更稳 |
| **有 GPU、几千条标注**，追事件级完全正确 | **BERT+CRF+解码期硬约束**（事件 0.218，论元 0.657） | LoRA SFT | Linear | 硬约束不重训，论元 **+7.5pp**、非法序列 62%→7.4%，延迟仅 40 ms |
| **延迟 < 15 ms** 或纯 CPU 在线服务 | **BERT+Linear**（11 ms，论元 0.563） | BiLSTM-CRF（21 ms，0.463） | BERT+CRF（74 ms） | CRF 用 6.6 倍延迟换 1.8pp 论元；Linear 是延迟/精度拐点 |
| **完全无 GPU、无预训练模型** | **BiLSTM-CRF**（CPU 1540 s，论元 0.463） | 规则 | BERT | 预训练值 **+11.8pp** 论元（0.463→0.581），但前提是有 GPU/权重 |
| **要求可解释、可审计、零训练** | **规则**（触发 0.617，论元 0.174，0.7~2.8 ms） | 规则+模型兜底 | LLM | 金额/日期/比例正则极强，公司名/标的物等自由文本论元几乎抽不对 |
| **schema 经常新增类型**，要按类型独立迭代 | **两段式**（论元 0.369） | 类型条件联合模型 | 单一大 joint（149 标签） | 精度更低（误差逐段放大），但新增类型只需重训一个专家，可定位“检测/类型/论元”哪段错 |
| **输出必须合法**（BIO/JSON 不能出现非法标签） | **CRF + 解码期硬约束**（非法 7.4%） | 受约束解码 + 校验层 | Linear（62%~67% 非法） | 金标自身因重叠论元有 **1.9% 非法地板**，不可能严格归零；硬约束已接近地板 |
| **篇章级多事件**（一篇公告多个事件） | **系统组合**：切句→检测→抽取→合并 | 长上下文 LLM | 单句 joint 直接喂整篇 | dev_docs 32% 的篇有 2 个以上事件（最多 6 个）；单条 BIO 序列只能表达一个事件 |
| **高并发、成本极敏感** | **规则 / BERT+Linear** | 蒸馏小模型 | API LLM | LLM 3.1~3.6 s/句且按 token 计费；规则 <3 ms |
| **结果要能解释“为什么抽错”** | **两段式 + 分层诊断** | BERT+CRF 的转移/发射分数 | 端到端黑盒 | 两段式天然输出检测置信度、类型概率、论元 span，可逐段定位 |

## 2. 决策树（按约束逐层排除）

```
有没有标注数据？
├─ 没有 ──► 能不能调外部 API？
│           ├─ 能 ──► API zero-shot（schema 固定、要快）
│           └─ 不能 ─► 规则（只求触发词/金额/日期）或本地小模型 zero-shot（接受低分）
└─ 有
    ├─ < 1,000 条 ──► API few-shot / zero-shot（先攒数据）
    ├─ 1,000~3,000 条 ──► BERT+CRF + 解码期硬约束
    └─ 3,000+ 条
        ├─ 有 8 GB 卡、追精度 ──► LoRA SFT（3,499 条 / 1 epoch 即超 BERT）
        ├─ 延迟 < 15 ms ──► BERT+Linear
        ├─ 要事件级/输出合法 ──► BERT+CRF + 解码期硬约束
        ├─ 无 GPU ──► BiLSTM-CRF（或规则兜底）
        └─ schema 常变/要可解释 ──► 两段式（检测→类型→论元）
```

## 3. 为什么是这些结论（三条反直觉发现）

1. **“更复杂的结构”不等于更高分。**
   两段式把 149 标签拆成“检测 + 13 分类 + 13 个专家”，标签空间小了一个数量级，
   但论元 F1 反而从 0.5815 掉到 0.3690。原因是**误差逐段放大**：检测漏 42.7%、
   类型错 5.5%，后面论元模型再准也救不回来。拆细适合“可维护/可解释”，不适合“刷分”。

2. **CRF 的主要价值不是“更准”，而是“更合法”。**
   Linear 有 66.9% 的句子会吐出非法 BIO；CRF 软约束仍有 62.5%，解码期硬约束压到 7.4%，
   论元只涨 1.8pp，但事件级从 0.156 涨到 0.218。**如果下游是结构化入库，合法性比 1~2pp 更重要。**

3. **3,499 条 SFT 打赢 5,747 条 BERT，是本周最划算的一格。**
   LoRA SFT 只训 1 epoch / 3,499 条、adapter 9 MB，触发 0.900 / 论元 0.697，
   比全量 BERT+CRF（5,747 条训练）高 11.7pp 论元；代价是 3.1 s/句、需要一张 8 GB 卡。
   **数据到三五千条、又想要最高精度时，优先考虑 LoRA，而不是继续堆 BERT 训练量。**

## 4. 本任务（金融公告、单句单事件）的最终建议

- **离线批量、追精度**：LoRA SFT（论元 0.697）。
- **在线服务、要合法结构化**：BERT+CRF+硬约束（事件 0.218、40 ms、不重训）。
- **极致延迟/降级兜底**：规则负责金额、日期、比例、已知触发词；模型负责公司名、标的物等自由文本论元。
- **新事件类型冷启动**：API zero-shot 先跑一版标注建议，人工改几百条、扩到千级后再转 LoRA SFT。
- **篇章级事件流**：不要指望单句模型，走 `service/` 的切句→检测→抽取→合并→校验链路。
